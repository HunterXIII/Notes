## Мини-словарь терминов (простыми словами)

### HTML-парсер
Компонент браузера, который превращает HTML-строку в DOM-узлы.  
Если вы делаете `element.innerHTML = "<div>...</div>"`, браузер запускает парсер, создаёт новые элементы и вставляет их в дерево.

### DOM
Объектное представление HTML-страницы в памяти (дерево узлов), с которым работает JavaScript.

### Reflow (layout, перерасчёт layout)
Этап, где браузер пересчитывает **размеры и позиции** элементов на странице.  
Это дорогая операция: если часто провоцировать reflow, интерфейс начинает тормозить.

### Repaint
Перерисовка визуальной части элементов (цвета, тени и т.д.) без изменения геометрии. Обычно дешевле reflow, но тоже может быть затратной.

### Event Loop
Главный цикл браузера: берёт задачи из очередей, выполняет JS, затем даёт шанс рендеру обновить кадр.

### Macrotask
Крупная задача очереди: `setTimeout`, `setInterval`, обработка DOM-событий, `postMessage` и т.п.

### Microtask
Задача "поверх" macrotask, выполняется сразу после текущего стека: `Promise.then/catch/finally`, `queueMicrotask`.

### Capture-фаза (фаза перехвата)
Первая фаза распространения события: событие идёт **сверху вниз** (от `window/document` к целевому элементу).  
В `addEventListener` включается через `{ capture: true }`.

### Bubble-фаза (всплытие)
После целевого элемента событие идёт **снизу вверх** по дереву DOM. Это поведение по умолчанию для большинства обработчиков.

### GC (Garbage Collector)
Сборщик мусора: автоматически освобождает память от объектов, на которые больше нет достижимых ссылок.

### Detached DOM Tree
Узлы удалены со страницы, но остались в памяти из-за ссылок в JS.

### Write Barrier
Механизм в движке JS, который "подсвечивает" важные записи ссылок для корректной работы инкрементального/поколенческого GC.

### Hidden Class (Map) в V8
Внутренняя "форма" объекта (какие поля есть и в каком порядке добавлены).  
Стабильная форма помогает движку сильно ускорять доступ к свойствам.

### Promotion (New -> Old Space)
Перевод объекта из "молодой" памяти в "старую", если объект прожил достаточно долго или этого требуют условия памяти.

### New Space / Old Space
- **New Space**: область для новых, часто короткоживущих объектов.  
- **Old Space**: область для долгоживущих объектов.

### LOS (Large Object Space)
Спецобласть памяти для очень больших объектов в V8.

### Inline Cache
Оптимизация движка: кешируются данные о том, как быстро получить свойство/вызвать метод для объектов знакомой формы.

### `response.ok` в `fetch`
Булево поле: `true`, если HTTP-статус в диапазоне 200–299.  
Важно: `fetch` не бросает ошибку только из-за `404/500`, поэтому проверка `ok` нужна вручную.

### `AbortController`
Стандартный способ отменять асинхронные операции (например, `fetch`) на уровне API, а не просто "игнорировать результат".

## Билет 1

### Вопрос 1. Живые и статические коллекции в Blink

**Простыми словами:** живая коллекция "смотрит" на текущий DOM в реальном времени, а статическая — это как фото экрана в момент запроса.

`HTMLCollection`/живые `NodeList` (например, `getElementsByClassName`, `childNodes`) связаны с DOM-деревом "по ссылке". Движок хранит структуру коллекции как представление запроса к текущему дереву, а не как окончательный снимок. Когда DOM меняется, коллекция либо инвалидируется, либо пересчитывается лениво при следующем доступе.

`querySelectorAll` возвращает статический `NodeList`: это снимок результата на момент вызова. Дальнейшие изменения DOM не обновляют этот список.

Почему `length` живой коллекции в цикле может быть дорогим:
- при каждом чтении `length` движок может проверять, не устарела ли коллекция;
- если устарела, выполняется пересчёт соответствия селектору/условию;
- при сложном DOM это может дать повторные обходы дерева;
- в цикле вида `for (let i = 0; i < live.length; i++)` получаем риск `O(n^2)` вместо `O(n)`.

Практика: кешировать длину (`const len = live.length`) или использовать статический снимок, если нужны стабильные данные.

### Вопрос 2. Почему у `fetch` проверяют `response.ok` вручную

**Простыми словами:** для `fetch` код `404` — это не "поломка интернета", а нормальный ответ сервера, поэтому ошибка не бросается автоматически.

`fetch` разделяет:
- **сетевой/транспортный провал** -> `Promise` отклоняется (`reject`);
- **HTTP-ответ сервера** (включая `404`, `500`) -> `Promise` успешно выполняется (`resolve`) с объектом `Response`.

Поэтому `404` у `fetch` не является исключением на уровне промиса: это "успешно полученный HTTP-ответ", просто со статусом ошибки. Проверка `response.ok` (или `status`) обязательна для бизнес-логики.

Когда `fetch` действительно уходит в `reject`:
- сбой сети (DNS, offline, reset соединения);
- CORS-блокировка;
- прерывание через `AbortController`;
- другие ошибки уровня транспорта/безопасности.

## Билет 2

### Вопрос 1. Detached DOM Tree и утечки в SPA

**Простыми словами:** элемент удалили со страницы, но если переменная на него всё ещё указывает, он остаётся в памяти.

Detached DOM Tree — это поддерево, удалённое из документа, но всё ещё достижимое по ссылкам из JS. Пока на узлы есть достижимые ссылки, GC не может их удалить.

Типичный сценарий утечки через живую коллекцию в долгоживущем объекте:
1. В приложении создаётся секция UI с множеством узлов.
2. Код сохраняет `HTMLCollection` (или объект, который замыкает/удерживает эти узлы) в глобальном сервисе/синглтоне.
3. Секция удаляется из DOM при смене экрана.
4. Ссылки в синглтоне остаются.
5. Узлы становятся detached, но достижимыми, поэтому не собираются.
6. При многократной навигации память растёт.

### Вопрос 2. `Promise.all` vs `Promise.allSettled` при ошибке

**Простыми словами:** `all` падает на первой ошибке, `allSettled` всегда ждёт всех и возвращает полный отчёт.

- `Promise.all([...])`:
  - завершится `rejected`, как только первый промис отвергнется;
  - результат успешных промисов не возвращается в итоговом значении;
  - хорош, когда нужна "атомарность": либо всё успешно, либо ошибка.

- `Promise.allSettled([...])`:
  - дождётся завершения **всех** промисов;
  - вернёт массив объектов `{ status: "fulfilled", value }` или `{ status: "rejected", reason }`;
  - подходит для частично успешных сценариев (агрегация, отчёты, best effort).

## Билет 3

### Вопрос 1. `innerHTML`, `textContent`, `innerText` в Blink

**Простыми словами:** `innerHTML` работает с HTML-разметкой, `textContent` — просто с текстом, `innerText` — с "тем, что реально видно на экране".

`innerHTML`:
- **чтение**: сериализация DOM-узлов в HTML-строку;
- **запись**: запускается HTML-парсер, строится новое поддерево, старое заменяется;
- может быть дорогим из-за парсинга, аллокаций и инвалидирования дерева;
- опасен для XSS при вставке недоверенного ввода.

`textContent`:
- **чтение**: конкатенация текстовых узлов без учёта CSS/видимости;
- **запись**: создаёт/обновляет текст, не парсит HTML;
- обычно самый предсказуемый и быстрый способ вставки текста.

`innerText`:
- учитывает "видимый" текст (стили, скрытые элементы, переносы);
- чтение часто требует актуализации layout/style, поэтому может вызывать синхронный reflow;
- обычно медленнее `textContent`, особенно на больших документах.

Итого по производительности (в среднем): `textContent` быстрее и безопаснее для текста; `innerHTML` нужен для контролируемой HTML-разметки; `innerText` — когда важна именно визуальная интерпретация текста.

### Вопрос 2. Что возвращает `then`

**Простыми словами:** `then` всегда создаёт новый промис, поэтому цепочки работают шаг за шагом.

`then` **всегда** возвращает новый промис.

Если колбэк:
- возвращает обычное значение (например, число) -> новый промис резолвится этим значением;
- возвращает промис -> новый промис "усыновляет" его состояние (ждёт и получает его итог);
- бросает исключение (`throw`) -> новый промис становится `rejected` с этой ошибкой.

Это и есть основа "цепочек промисов": каждый шаг преобразует либо прокидывает состояние дальше.

## Билет 4

### Вопрос 1. Почему `AbortController` одноразовый

**Простыми словами:** если контроллер уже "нажал стоп", отмена остаётся навсегда — обратно включить нельзя.

`AbortController` переводит `signal` в состояние `aborted`, и это состояние необратимо. После `abort()` сигнал навсегда остаётся "отменённым".

Если использовать тот же сигнал во втором `fetch`, он может отклониться сразу (или считаться уже отменённым), потому что запрос подписывается на уже-aborted сигнал.

Правильный паттерн: новый `AbortController` на каждую независимую операцию/попытку.

### Вопрос 2. Реальная отмена vs "таймаут с reject"

**Простыми словами:** `AbortController` реально останавливает запрос, а `reject` по таймеру только делает вид, что "мы больше не ждём".

`AbortController`:
- реально сигнализирует API остановить I/O;
- освобождает сетевые/буферные ресурсы;
- даёт согласованный механизм отмены в экосистеме Web API.

`new Promise((_, reject) => setTimeout(reject, ...))` вокруг `fetch`:
- лишь создаёт альтернативный исход в пользовательском промисе;
- сам запрос обычно продолжает выполняться в фоне;
- можно получить гонки, лишний трафик, сложные состояния.

Поэтому "reject-таймаут без abort" — плохая практика: логическая отмена есть, физической остановки операции нет.

## Билет 5

### Вопрос 1. `onclick` и `addEventListener`

**Простыми словами:** `onclick` — один обработчик "в лоб", `addEventListener` — нормальный масштабируемый инструмент для проекта.

`onclick`:
- одно свойство -> один обработчик;
- перезапись уничтожает предыдущий;
- нет гибкой настройки phase/options;
- прост в очень маленьких сценариях (быстрый прототип, локальный одноразовый обработчик).

`addEventListener`:
- много обработчиков на одно событие;
- поддерживает `capture`, `once`, `passive`, `signal`;
- легче управлять жизненным циклом (`removeEventListener`, `AbortSignal`);
- лучше масштабируется и обычно предпочтителен в production.

С точки зрения памяти важен не API сам по себе, а управление жизненным циклом ссылок и очистка обработчиков.

### Вопрос 2. Трёхцветная маркировка и write barrier

**Простыми словами:** GC красит объекты в "цвета", а write barrier следит, чтобы из-за новых ссылок живой объект случайно не удалили.

Трёхцветная модель GC:
- **white**: ещё не отмечен как живой (кандидат на удаление);
- **grey**: найден живым, но его ссылки ещё не просканированы;
- **black**: живой и полностью просканирован.

Проблема конкурентной маркировки: если уже "чёрный" объект получает ссылку на "белый", белый объект может ошибочно остаться непомеченным и быть удалён.

Сценарий `black.field = white`:
1. `black` уже просканирован;
2. выполняется запись ссылки на `white`;
3. write barrier перехватывает запись и помечает цель/карту памяти (или переводит объект в grey);
4. GC гарантирует, что новая ссылка будет учтена.

Итог: write barrier сохраняет корректность инкрементальной/конкурентной маркировки.

## Билет 6

### Вопрос 1. Generational hypothesis и маленький New Space

**Простыми словами:** новые объекты чаще всего быстро умирают, поэтому для них делают маленькую, но очень быстро очищаемую область памяти.

Поколенческая гипотеза: "большинство объектов умирает молодыми". Поэтому выгодно часто и дёшево чистить маленькую молодую область.

Почему New Space небольшой:
- маленький объём -> очень быстрые Minor GC паузы;
- меньше данных для копирования/сканирования;
- лучше locality/cache.

Компромисс:
- слишком маленький New Space -> слишком частые Minor GC;
- слишком большой -> каждый Minor GC дороже и длиннее пауза.

Инженерно выбирается баланс пропускной способности и latency.

### Вопрос 2. Суть `Promise.race`

**Простыми словами:** `race` возвращает того, кто финишировал первым — не важно, успех это или ошибка.

`Promise.race(iterable)` завершается состоянием **первого завершившегося** участника (успех или ошибка).

Когда лучше `race`, чем `all`/`any`:
- таймауты и "кто быстрее";
- выбор быстрейшего зеркала/реплики;
- прекращение ожидания после первого доступного результата.

`all` ждёт всех, `any` ждёт первого **успешного**, а `race` реагирует на вообще первое завершение.

## Билет 7

### Вопрос 1. Почему транзакция IndexedDB "умирает" через `setTimeout`/`Promise.resolve`

**Простыми словами:** транзакция IndexedDB живёт очень "локально" — вышли из активного шага цикла событий, и она может закрыться.

IndexedDB-транзакция активна в рамках текущего "активного шага" event loop. Когда управление полностью возвращается в цикл задач, и в транзакции нет немедленно поставленной работы, браузер считает транзакцию завершённой/неактивной.

Даже `setTimeout(..., 0)` — новый macrotask, а `Promise.resolve().then(...)` — микрозадача после текущего стека; в ряде сценариев это уже за пределами активного окна транзакции.

Архитектурная цель: детерминированность и автоматическое закрытие транзакций, чтобы не держать блокировки БД дольше нужного.

### Вопрос 2. Scavenge vs Mark-Compact и promotion

**Простыми словами:** молодую память чистят быстро и часто, старую — реже, но тяжелее; "взрослые" объекты переезжают в старшее поколение.

Scavenge (Minor GC):
- для New Space;
- копирующий алгоритм между semi-spaces;
- быстрый, ориентирован на короткоживущие объекты.

Mark-Compact (Major GC):
- для Old Space;
- маркирует живые объекты, потом уплотняет память;
- дороже, но борется с фрагментацией долгоживущих данных.

Promotion (New -> Old) — перевод объекта в старшее поколение, когда он переживает несколько minor-сборок или при давлении памяти/политике allocator.

Типичные причины досрочного promotion:
- объект "выжил" нужное число minor циклов;
- нехватка места в To-space;
- крупные/особые объекты и эвристики движка.

## Билет 8

### Вопрос 1. Почему `await` не блокирует поток

**Простыми словами:** `await` не "замораживает" браузер — функция ставится на паузу, а поток продолжает обслуживать UI и события.

`await` преобразуется в продолжение через промисы:
1. функция доходит до `await`;
2. управление возвращается вызывающему коду;
3. оставшаяся часть функции планируется как микрозадача после резолва промиса.

Главный поток не "стоит", потому что стек вызова освобождается, event loop продолжает обрабатывать ввод, рендер и другие задачи.

### Вопрос 2. Hidden Classes в V8 и что ломает оптимизацию

**Простыми словами:** V8 любит одинаковую форму объектов; хаотичное добавление/удаление полей ломает ускорения.

Hidden Class (Map) — внутренняя "форма" объекта: набор свойств и порядок их добавления. JIT делает быстрые inline cache, когда форма стабильна.

Что ломает оптимизацию:
- добавление свойств в разном порядке у экземпляров;
- удаление свойств (`delete`);
- динамическая смена типов/структуры "на лету";
- мешанина "словарного" стиля вместо стабильной схемы.

"Хороший" стиль: инициализировать полный набор полей в конструкторе в одинаковом порядке.  
"Плохой": частично создавать поля позже и по-разному у разных объектов.

## Билет 9

### Вопрос 1. Классическое vs прототипное наследование

**Простыми словами:** в JS объект чаще "спрашивает у прототипа", если сам не знает свойства.

В классической модели (Java/C++): поведение задаётся классами, структура обычно жёстко объявлена заранее.

В JS-прототипах: объект делегирует поиск свойства по цепочке `[[Prototype]]`. Нет копирования методов в каждый объект; есть динамическое делегирование.

Пример делегирования: если у `obj` нет `foo`, движок ищет `foo` у прототипа, затем выше по цепочке.

### Вопрос 2. Потеря `this` в обычных функциях в промисах

**Простыми словами:** обычная функция в `then` теряет владельца, поэтому `this` уже не указывает на экземпляр класса.

У обычной функции `this` определяется способом вызова. В `then(function () {})` вызов идёт без контекста объекта, поэтому `this` теряется (в strict-mode — `undefined`).

Способы исправить в методе класса:
- стрелочная функция в колбэке (`then(() => this.x)`) — лексический `this`;
- `bind(this)` для обычной функции;
- сохранить ссылку (`const self = this`) и использовать её в колбэке.

## Билет 10

### Вопрос 1. Правило "чтение vs запись" в прототипах

**Простыми словами:** чтение идёт вверх по цепочке прототипов, а запись обычно создаёт поле прямо в текущем объекте.

Чтение: поиск идёт вверх по прототипной цепочке.  
Запись: обычно создаётся/обновляется **собственное** свойство объекта-получателя, не меняя прототип.

Shadowing (затенение): собственное свойство с тем же именем скрывает прототипное при чтении.

Когда присваивание не создаёт собственное свойство:
- если в прототипе найден accessor без setter или non-writable data property, запись не может создать обычное поле как обычно (в strict-mode — ошибка, вне strict — молчаливый провал).

### Вопрос 2. Пространства памяти V8

**Простыми словами:** V8 делит кучу на специализированные зоны: отдельно для новых объектов, старых, кода, карт форм и больших объектов.

Ключевые spaces:
- New Space (молодые объекты);
- Old Space (долгоживущие объекты);
- Code Space (машинный код JIT);
- Map Space (hidden classes/maps);
- Large Object Space (крупные объекты);
- часто также Read-Only Space.

Назначение:
- Map Space: метаданные форм объектов, критично для inline cache;
- Code Space: исполняемый код со спецограничениями памяти/прав доступа;
- LOS: объекты, слишком большие для обычных страниц, обычно без перемещения.

LOS vs Old Space:
- в LOS объекты обычно не компактизируются как обычные мелкие объекты;
- это снижает стоимость перемещения больших блоков, но требует другой политики управления фрагментацией.

## Билет 11

### Вопрос 1. Поведенческие отличия class от функции-конструктора

**Простыми словами:** классы сделали более "безопасными по умолчанию", чтобы меньше ловить неожиданные ошибки.

Три важных отличия:
- классы нельзя вызвать без `new` (защита от случайного вызова);
- методы класса не перечисляются в `for...in` (менее шумный объектный интерфейс);
- тело класса работает в strict mode по спецификации.

Дополнительно: у class есть встроенная семантика `super`, более предсказуемое наследование и явная структура API.

### Вопрос 2. Page mask в V8 и почему это быстро

**Простыми словами:** по адресу объекта V8 очень быстро (битовой операцией) находит нужную страницу памяти и служебные структуры GC.

Куча делится на страницы фиксированного размера. Побитовое маскирование адреса объекта (page mask) быстро даёт базовый адрес страницы (`MemoryChunk`), без поиска в таблицах.

Зная страницу и смещение, легко вычислить индекс в card table для write barrier.

Почему важно:
- write barrier выполняется очень часто при записях ссылок;
- дешёвая адресная арифметика снижает накладные расходы;
- напрямую влияет на общую производительность движка.

## Билет 12

### Вопрос 1. Почему `super()` нужен до `this` в наследнике

**Простыми словами:** пока не вызван `super()`, у наследника ещё нет корректно созданного `this`.

В derived-классе `this` не инициализирован до вызова конструктора родителя. `super()` создаёт/инициализирует базовую часть экземпляра и связывает корректный `this`.

Если обратиться к `this` раньше `super()`, это ошибка времени выполнения (`ReferenceError`).

Смысл правила: гарантировать корректную инициализацию цепочки наследования.

### Вопрос 2. Три типичных сценария утечек памяти в JS

**Простыми словами:** чаще всего память "течёт", когда мы забыли снять слушатель, остановить таймер или отпустить замыкание с большими данными.

Частые источники:
- забытые обработчики событий на долго живущих объектах;
- таймеры/интервалы, которые не очищаются;
- замыкания, удерживающие большие структуры после потери бизнес-необходимости.

Механизм на примере замыкания:
- функция-обработчик захватывает `bigData`;
- обработчик хранится в достижимом месте (DOM/глобал);
- даже если внешний контекст "логически не нужен", `bigData` остаётся достижимым через closure;
- GC не удаляет объект до разрыва этой цепочки ссылок.

## Билет 13

### Вопрос 1. `_field` vs `#field`

**Простыми словами:** `_name` — это просто договорённость, а `#name` — настоящая защита на уровне языка.

`_field` — договорённость по имени, но не техническая защита: доступ возможен извне.

`#field` — настоящая приватность на уровне языка:
- доступ только внутри тела класса;
- нельзя прочитать/записать извне и из несвязанных объектов;
- не участвует в обычном перечислении свойств.

Когда `_field` всё ещё уместен:
- нужна "защищённость по соглашению" для подклассов/метапрограммирования;
- требуется совместимость со старым инструментарием/транспиляцией;
- нужен доступ в экосистеме, где жёсткая приватность мешает расширяемости.

### Вопрос 2. Bump-pointer vs FreeList и Lazy Sweeping

**Простыми словами:** молодая память выделяется "бегунком" очень быстро, старая — через поиск подходящих дырок в свободных блоках.

New Space:
- `bump-pointer allocation`: просто двигаем указатель вперёд;
- экстремально быстрые аллокации при короткой жизни объектов.

Old Space:
- `FreeList allocation`: используется список свободных блоков разных размеров;
- подходит для долгоживущих объектов и менее регулярного освобождения.

Lazy Sweeping:
- очистка/возврат свободных блоков выполняется постепенно, по мере необходимости;
- уменьшает длинные стоп-паузы после major-сборки.

## Билет 14

### Вопрос 1. Как работает `super.method()` и `[[HomeObject]]`

**Простыми словами:** `super` ищет метод в прототипе того объекта, где метод был объявлен, а не просто "где-то у this".

Для методов, объявленных синтаксисом метода, движок сохраняет `[[HomeObject]]` — объект, где метод был определён.  
`super.method()` ищет метод не от `this`, а от прототипа `[[HomeObject]]`, затем вызывает его с текущим `this`.

Почему стрелочные функции в поле класса не используют `super` так же:
- стрелка не создаёт собственный method-definition с подходящим `[[HomeObject]]` в том же смысле;
- она лексически захватывает контекст и не предназначена как полноценный "прототипный метод" для механики `super`.

### Вопрос 2. Проблема ссылок old -> new и роль card table

**Простыми словами:** чтобы не проверять всю старую память при каждом minor GC, движок помечает только те участки, где были важные записи ссылок.

Minor GC сканирует в основном New Space. Но если Old Space содержит ссылку на новый объект, её нужно учесть, иначе новый объект ошибочно удалится.

Наивно сканировать весь Old Space каждый minor цикл слишком дорого.

Решение:
- write barrier при записи `oldRef.field = newRef` помечает соответствующую "карту" (card);
- minor GC проверяет только отмеченные card regions, а не весь Old Space;
- получаем корректность при приемлемой цене.

## Билет 15

### Вопрос 1. Наследование от встроенных классов и `Symbol.species`

**Простыми словами:** `Symbol.species` подсказывает, какого типа объект должны возвращать методы вроде `map`/`filter`.

У встроенных классов (например, `Array`) фабричные методы (`map`, `filter` и т.д.) создают новый экземпляр согласно внутренним правилам конструктора-результата.

`Symbol.species` позволяет определить, какой конструктор использовать для производных операций.

Если в наследнике корректно настроить `static get [Symbol.species]()`, можно контролировать, вернут ли методы экземпляр наследника или базового типа.

Это важно для предсказуемости API библиотек и избежания "сломанных" цепочек методов.

### Вопрос 2. Почему рендер — отдельная фаза

**Простыми словами:** отрисовка кадра — это особый этап браузера, который идёт по своему ритму, а не просто "ещё одна задача очереди".

Event Loop в браузере включает не только macrotask/microtask, но и этапы обновления отображения (style/layout/paint/composite). Рендер — отдельная подсистема, синхронизированная с кадровым циклом.

Браузер входит в фазу обновления, когда:
- текущая задача завершена;
- обработаны микрозадачи;
- есть invalidations (изменения DOM/CSSOM/геометрии);
- наступает время кадра.

Если поток бесконечно занят макрозадачами без "окон" на кадр, анимация начинает лагать/замораживаться из-за starvation рендера.

## Билет 16

### Вопрос 1. Предпочитайте композицию наследованию

**Простыми словами:** собирать поведение из частей обычно проще и надёжнее, чем строить длинную цепочку наследования.

Композиция ("has-a") уменьшает жёсткую связанность и хрупкость глубоких иерархий ("is-a"), где изменение базового класса ломает поведение потомков.

Проблема глубокой иерархии:
- трудно предсказать влияние override;
- "взрыв" условной логики в базовых классах;
- сложнее тестирование и повторное использование.

Композиция решает это через набор независимых компонентов/стратегий, которые можно комбинировать и менять без перестройки всей иерархии.

### Вопрос 2. Hoisting: `var`, `let`, `const`, function declaration

**Простыми словами:** JavaScript "видит" объявления заранее, но ведут они себя по-разному до строки инициализации.

Hoisting — фаза создания окружения до выполнения кода.

- `function declaration`: поднимается целиком, можно вызывать до объявления.
- `var`: поднимается и инициализируется `undefined`; чтение до присваивания допустимо.
- `let`/`const`: поднимаются, но находятся в TDZ до фактического объявления; доступ раньше — `ReferenceError`.

TDZ предотвращает использование переменной до корректной инициализации и снижает класс ошибок, характерных для `var`.

## Билет 17

### Вопрос 1. `toJSON`: зачем нужен

**Простыми словами:** `toJSON` — способ самому решить, в каком виде объект уйдёт в JSON.

`toJSON` — специальный метод, который `JSON.stringify` вызывает для кастомной сериализации.

Практическая польза:
- исключение чувствительных полей (пароли, токены);
- нормализация формата (даты, enum, DTO);
- обход несовместимых структур.

Важно: `toJSON` не "лечит" циклические ссылки автоматически, но позволяет вручную вернуть сериализуемое представление и убрать цикл из результата.

### Вопрос 2. Почему IndexedDB есть в Worker, а `localStorage` — нет

**Простыми словами:** `localStorage` слишком "блокирующий", а IndexedDB асинхронный и лучше подходит для фоновой работы.

`localStorage` синхронный и блокирует поток, поэтому в многопоточном окружении это плохо масштабируется и создаёт contention.

IndexedDB асинхронный, транзакционный и лучше подходит для worker-контекста.

Выигрышные сценарии в воркерах:
- обработка больших массивов данных;
- inference/подготовка ML-артефактов;
- видеопроцессинг/медиа пайплайны;
- сохранение промежуточных результатов без блокировки UI.

## Билет 18

### Вопрос 1. Почему `for..in` бывает "неожиданным"

**Простыми словами:** `for..in` может вернуть не только "ваши" ключи, но и унаследованные, поэтому с объектами-словариками с ним легко ошибиться.

`for..in` перечисляет перечисляемые свойства по всей прототипной цепочке, а не только собственные. Поэтому можно получить лишние ключи от прототипа/полифиллов.

Чтобы взять только собственные перечисляемые ключи:
- `Object.keys(obj)` -> массив собственных enumerable-ключей;
- `Object.entries(obj)` -> пары `[key, value]`;
- фильтр через `Object.hasOwn(obj, key)` при необходимости.

"Чистый словарь" — объект без прототипа:
- `Object.create(null)`;
- не наследует `Object.prototype`, поэтому нет коллизий с `toString`, `constructor` и т.п.

### Вопрос 2. Виды функций и hoisting

**Простыми словами:** разные виды функций "всплывают" по-разному: одни можно вызвать раньше, другие — нет.

Типы:
- function declaration;
- function expression;
- arrow function;
- generator function (`function*`).

По hoisting:
- declaration поднимается как функция и доступна до места объявления;
- expression/arrow зависят от переменной-носителя:
  - если `var`, переменная поднимется как `undefined` (вызов до присваивания -> ошибка типа "not a function");
  - если `let/const`, действует TDZ;
- generator declaration поднимается аналогично function declaration (как объявление функции).

Итого: "поднимается" не равно "готово к вызову" для expression/arrow.

## Билет 19

### Вопрос 1. `requestAnimationFrame` vs `setTimeout(f, 0)`

**Простыми словами:** `rAF` синхронизирован с кадрами экрана, поэтому для анимации и DOM-обновлений обычно лучше, чем `setTimeout(0)`.

`setTimeout(..., 0)` ставит macrotask "как можно раньше", но не синхронизирует выполнение с кадром и может сработать в неудачный момент для рендера.

`requestAnimationFrame` вызывается перед отрисовкой следующего кадра. Поэтому изменения DOM/стилей в rAF лучше попадают в текущий render pipeline и дают более плавную анимацию.

`postMessage` иногда используют как быстрый источник macrotask без таймерных ограничений, когда нужно планирование с меньшими задержками, чем у таймеров (особенно под throttling).

### Вопрос 2. Ограничения и модель Web Worker

**Простыми словами:** worker — это отдельный "мини-поток" без доступа к DOM, который общается с основной страницей сообщениями.

Ограничения worker:
- нет прямого доступа к DOM;
- свой глобальный контекст (`self`), другой набор API;
- общение с main thread через message passing (или SharedArrayBuffer/Atomics при особых условиях).

Что получает каждый worker:
- собственный event loop;
- собственный стек вызовов и очереди задач;
- изолированную память (кроме явно разделённой).

Сравнение с Java/C++:
- в браузере по умолчанию безопасная изоляция и обмен сообщениями;
- в классических потоках общий адресный простор и явная синхронизация (mutex/locks), что гибче, но опаснее (гонки, deadlock).

## Билет 20

### Вопрос 1. Кооперативная многозадачность и `requestIdleCallback`

**Простыми словами:** `requestIdleCallback` — это "сделай, когда браузер не занят чем-то важнее".

Идея кооперативности: тяжёлую несрочную работу выполнять малыми порциями, уступая управление важным задачам (ввод, анимация, рендер).

`requestIdleCallback` запускает колбэк, когда у цикла есть "окно простоя". Практически это состояние, где:
- нет более приоритетной немедленной работы;
- есть бюджет времени до следующего дедлайна кадра.

Правило безопасности для DOM:
- в `rIC` делать вычисления/подготовку данных;
- критические DOM-мутации лучше переносить в rAF/основной шаг, чтобы не вносить jank перед кадром.

### Вопрос 2. Batch-запись из воркера в IndexedDB, пул воркеров, `SharedArrayBuffer`

**Простыми словами:** большие записи в IndexedDB лучше делать порциями и контролировать параллелизм, иначе можно перегрузить систему.

Batch-запись:
- группировать операции в контролируемые транзакции;
- ограничивать размер батча, чтобы снижать длительность блокировок;
- подтверждать прогресс порциями, а не одной гигантской транзакцией.

"Один воркер на транзакцию":
- проще модель, но выше накладные расходы на создание/координацию.

"Пул воркеров":
- лучше утилизация ресурсов;
- нужен планировщик задач и контроль конкуренции за IndexedDB.

Почему `SharedArrayBuffer` усложняет GC:
- появляется разделяемая память и более сложные графы достижимости между потоками;
- требуются дополнительные гарантии согласованности и аккуратное управление временем жизни данных.
